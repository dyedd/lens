# 接入站点与模型

操作示例使用 `gpt-6.1-sol`、`gpt-6-luna` 和 `claude-opus-5-5`。模型 ID 与能力以官方的 [GPT-6.1 Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)和 [Claude Opus 5.5](https://platform.claude.com/docs/en/models/opus-5-5/overview) 文档为准；接入时从当前供应商返回的目录中选择。

在 **渠道** 页面维护服务商的地址、API Key 和模型。一条渠道记录可以包含多个地址和多把 Key。

接入前准备好服务商的 Base URL、API Key，以及该账号允许调用的模型。下面截图使用本地演示上游；实际接入时替换为服务商提供的值。

可以先接入一个渠道、一把 Key 和一个模型，完成调用后再增加备用供应商。渠道中的 Key 用于 Lens 访问供应商，客户端使用的网关 Key 在 [客户端接入](./clients) 中创建。

## 新建渠道

1. 打开 **渠道**，点击 **新建渠道**。
2. 填写渠道名称和接口地址；标签可用于后续筛选。
3. 添加 API Key，填写易辨认的凭证名称。
4. 按需设置凭证适用的地址，然后保存。

![渠道列表及新建渠道入口](/images/channels.png)

![渠道编辑弹窗中的地址、标签、凭证和代理设置](/images/channel-editor.png)

填写 Base URL 即可，不要填写单次请求的完整路径。例如填写 `https://api.openai.com`，而不是 `https://api.openai.com/v1/chat/completions`。

| 上游 | 地址示例 |
| --- | --- |
| OpenAI | `https://api.openai.com` |
| Anthropic | `https://api.anthropic.com` |
| Gemini | `https://generativelanguage.googleapis.com` |
| 兼容服务 | 服务商提供的 Base URL，例如 `https://api.example.com` |

“其他地址”用于配置同一站点的额外出口。地址用途决定它承接哪些接口；同一 Key 可限制为指定地址。需要代理时，在渠道的 **代理设置** 中选择继承全局、直连或自定义代理。

例如，同一服务商分别提供 Chat 和 Responses 地址，可以把两个地址放在同一渠道中。如果 A-Key 只适用于 Chat 地址，就只勾选该地址。两处地址使用相同协议，并不说明它们接受同一把 Key。用途为 **模型列表** 的地址用于获取目录，不参与推理请求。

保存渠道只代表地址和凭证已存入 Lens。模型还需要接入、归组并通过实际调用，才能确认整个链路可用。

## 获取模型

新建渠道保存后会进入模型选择流程。已有渠道可从行末 **操作 → 管理模型** 打开模型列表，再点击 **获取模型列表**。

1. 获取上游模型列表。
2. 勾选要接入的模型，检查该名称下显示的来源地址和凭证。
3. 确认接入，返回模型列表检查上游协议、启停和上下文，再点击 **保存**。
4. 返回渠道列表，检查已启用模型数量。

![获取上游模型并选择接入项](/images/remote-models.png)

![已接入模型的凭证、上游协议、启停状态与上下文](/images/channel-models.png)

模型选择器按名称汇总来源。选择一个名称会加入它列出的来源；“部分接入”表示同名模型仍有来源尚未加入。确认接入后先更新编辑中的模型列表，点击 **保存** 才会写入渠道。

接入动作也会把选中的模型名合并到对应 Key 的同步规则中，使后续同步继续跟踪这些模型。保存后打开 **模型组**，查看它们加入了现有组、新建了同名组，还是进入待分配列表。

上游协议的默认值来自模型元数据和规则，并非逐个发送推理请求探测得到。默认值不符合实际接口时，可直接修改 **上游协议**。例如某个兼容服务用 OpenAI Chat 接口提供 Claude 模型，应选择它实际提供的 Chat 协议。

模型身份包含渠道、Key 和上游模型名。两把 Key 下的同名模型是两个成员，不应因为名字相同就把它们当成同一个账号配额。

## 控制自动同步范围

点击模型列表中的 **模型规则**，为每把 Key 设置要保留的模型。规则作用于该 Key 的上游目录，匹配时不区分大小写：

| 规则 | 结果 |
| --- | --- |
| 留空 | 跳过这把 Key 的自动同步，保留现有模型 |
| `*` | 接入目录中的全部模型 |
| `gpt-6.1-sol` | 只匹配完整名称 `gpt-6.1-sol`，不包含 `gpt-6-luna` |
| `^gpt-.*$` | 接入所有以 `gpt-` 开头的模型 |
| `^(gpt-6\.1-sol|gpt-6-luna)$` | 只保留列出的两个完整名称 |

普通名称按精确名称匹配，正则按完整名称匹配；模型名中的点在普通名称里就是点。**这里与模型组名称的“包含匹配”不同**，见 [模型组匹配范围](./model-groups#设置匹配范围)。

例如，上游返回 `gpt-6.1-sol`、`gpt-6-luna`、`text-embedding-3-small`，规则为 `^gpt-.*$`，同步后前两个模型进入该 Key 的模型列表，第三个不进入。把规则改成 `gpt-6-luna` 后再同步，已有的 `gpt-6.1-sol` 也会被移除。因此，缩小规则前应确认哪些模型仍被使用。

每次同步按地址和 Key 分别处理：

| 情况 | 保存结果 |
| --- | --- |
| 目录拉取成功，出现新的匹配模型 | 加入模型，随后重新归组 |
| 已有模型不匹配规则，或不再出现在成功返回的目录里 | 从该 Key 的模型列表移除，相关自动组成员也会更新 |
| 已有模型仍匹配 | 保留启停、手动上下文和协议等设置，更新上游报告的上下文 |
| 某个目录拉取失败 | 该目标保留原有模型；其他成功的目标继续同步 |
| 规则为空 | 不拉取这把 Key 的目录，不调整它的模型列表 |

规则管理的是该 Key 的整个模型列表，手动添加的模型同样受非空规则约束。无法从目录发现、但确实可调用的模型，可以手动填写模型名、Key 和协议，并把该 Key 的规则留空来手动维护。

在界面修改规则并保存时，会同步受影响的 Key；定期同步由 **设置 → 计划任务 → 渠道模型同步** 控制。同步后，在 **模型组 → 同步记录** 检查新增、移除、归组、待分配和获取失败的目标。出现部分失败时，先修复对应地址、Key 或代理，再重新同步，不需要删除整个渠道。

## 设置上下文与验证

可以在模型表格或接入弹窗中填写上下文窗口。单个模型的手动值优先；未配置时可使用上游返回的值或模型组默认值。

接入后打开 [模型组](./model-groups)，确认模型已有可用成员，再使用 **测试模型** 验证。测试会向上游发出实际请求，可能产生用量。

| 现象 | 检查位置 |
| --- | --- |
| 获取模型失败 | 地址、Key、代理；服务商是否提供模型列表接口 |
| 模型同步后消失 | Key 的模型规则，以及上游是否仍返回该模型 |
| 模型可见但调用失败 | 上游协议、凭证权限、模型启用状态和请求日志 |
| 同名模型出现多次 | 是否分别属于不同 Key 或不同渠道 |
