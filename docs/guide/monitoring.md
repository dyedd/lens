# 查看用量与排查请求

先用 **概览** 找到异常时段，再用 **请求日志** 定位具体请求，最后结合 **健康状态** 判断是否存在冷却或上游故障。

本页截图使用演示请求和本地上游，费用与成功率仅用于说明界面。

## 查看概览

![概览中的请求量、成功率、Token、缓存命中率和趋势](/images/overview.png)

1. 在右上角选择时间范围。
2. 查看请求量、成功率、预计成本和 Token 用量。
3. 切换趋势指标，查看请求、Token、成本或总时长。
4. 在下方按模型、渠道或 Agent 查看归因；展开条目或点击比较渠道，定位主要来源。

成本由模型价格、实际用量和凭证倍率等配置计算。发现费用为零或与服务商账单不一致时，先检查 **价格** 页面及实际使用的上游模型。Lens 的统计不代替服务商最终账单。

## 定位一次请求

![请求日志中的模型、协议、耗时和用量](/images/request-logs.png)

1. 打开 **请求日志**，使用搜索与筛选缩小时间、状态、模型或渠道范围。
2. 点击请求行，打开详情。
3. 查看请求模型、执行组、实际渠道、首 Token 耗时、总耗时和用量。
4. 对于最终失败的请求，向下查看 **尝试**，逐次比较状态码、错误原因和耗时。

![失败请求详情中的上游尝试、状态码和错误](/images/request-detail.png)

一次客户端请求可能包含多次上游尝试。当前详情页只在最终失败时展开尝试列表，成功请求主要展示最终渠道和用量。需要查看成功请求的完整尝试记录时，可用管理员认证查询 `GET /api/admin/request-logs/{log_id}`，读取 `attempts` 字段。

例如，客户端请求 `daily-chat`，A 返回 429，Lens 转到 B 并得到正常回复：

| 观察位置 | 应怎样理解 |
| --- | --- |
| 请求列表 | 这仍是一个最终成功的客户端请求，最终渠道为 B |
| 请求模型与执行组 | 请求名称可以是别名 `daily-chat`，执行组可以是 `gpt-6.1-sol` |
| 完整尝试记录 | 可看到 A 的限流和 B 的成功；不能只凭最终 200 判断所有上游都健康 |
| 总耗时 | 包含前面的失败尝试和等待，可能明显长于 B 自己的响应时间 |
| 健康与冷却 | 即使本次最终成功，A 对应的目标仍可能处于冷却 |

查看耗时时，先确认是非流式请求还是流式请求。流式请求的首 Token 时间表示等待开始输出的时间，总耗时还包括后续生成过程。相同输入下首 Token 接近、总耗时不同，可能只是输出长度不同，不能直接认定为连接异常。

状态含义：

| 状态 | 含义 |
| --- | --- |
| 连接中 | 已接收请求，正在路由或等待上游 |
| 流式中 | 正在向客户端传输流式响应 |
| 成功 | 请求正常结束 |
| 失败 | 请求最终未成功，查看错误与尝试链 |
| 已取消 | 客户端断开等原因使请求取消 |

流式响应可能已经以 HTTP 200 开始，但随后在事件流中失败。此时应结合最终状态、错误信息和已输出内容判断。

如果客户端已收到部分文本，Lens 无法撤回它并换一个上游从头重放。排查时同时保留客户端最后收到的事件和对应请求详情，区分上游中断、空闲超时和主动取消。故障转移发生的阶段见 [流式响应的边界](../development/architecture#流式响应的边界)。

## 查看请求与响应正文

在 **设置 → 网关** 开启请求体 / 响应体记录后，新请求的详情可以展示正文，并支持复制 cURL。

正文可能包含提示词、业务数据和上游输出。只在需要时启用，并配置日志留存。之前未记录的正文无法通过开关恢复。

复制的请求仅作为复现起点，执行前确认地址、网关 Key 和请求内容。

## 查看健康与冷却

![健康状态中的成功率、时间线、剩余冷却与重置操作](/images/model-health.png)

健康页可按模型组或渠道查看统计。**成功率反映所选时间窗口中的请求结果，剩余冷却反映当前路由状态**，两者可能不同。组中某个成员冷却时，备用成员仍可能成功处理请求。

一行的剩余冷却显示其相关目标中的最长剩余时间。例如 A 还需 120 秒、B 已可用，这一行仍可显示 120 秒，但请求可以由 B 接管。它不表示整组必须等待 120 秒。

处理步骤：

1. 看剩余冷却时间，确认是临时限流还是持续故障。
2. 回到请求详情，查看对应 Key 或上游模型的失败原因。
3. 修正凭证、地址、配额或服务商故障。
4. 需要立即重新尝试时，点击该行的 **重置冷却**。
5. 发出测试请求，确认结果；如果故障仍存在，冷却可以再次触发。

`401 / 403 / 429` 通常影响当前 Key；`404 / 5xx / 超时 / 网络错误` 通常影响当前上游模型。多把 Key 同时限流可升级为模型冷却。规则和上限见 [配置参考](../reference/configuration#冷却与健康排序)。

重置冷却只清除当前路由的等待状态，不会修改 Key、恢复服务商配额或删除历史失败记录。共享 Key 或相同冷却目标的其他模型也会解除对应冷却，因此重置后成功率不会立刻归零或变成 100%。

## 常见排查顺序

| 现象 | 检查顺序 |
| --- | --- |
| 401，且没有请求日志 | 先查网关 Key 是否有效、启用、到期或达到费用上限；入口认证失败发生在请求日志创建之前 |
| 尝试记录中出现 401 / 403 | 查该次上游 Key 的权限、适用地址和服务商账号状态 |
| 429 后频繁换渠道 | 服务商配额、Key 冷却、重试等待时间 |
| 503 且带 Retry-After | 先查全部候选是否冷却及等待设置；没有重试时间时同时检查组内可用成员 |
| 首 Token 很慢 | 上游首响应、网络和代理；检查首响应超时设置 |
| 流式中途断开 | 流式空闲超时、上游事件错误、客户端取消 |
| 同一请求费用异常 | 上游模型、价格覆盖、缓存 Token 和凭证倍率 |
