# 管理模型组

客户端的 `model` 填写 **模型组名称**。模型组把多个渠道、Key 和上游模型组织为一个可调用入口。

本页用一个主备配置说明：供应商 A 和 B 都已接入 `gpt-6.1-sol`，先让执行组 `gpt-6.1-sol` 管理这两个成员，再用别名 `daily-chat` 提供稳定的客户端名称。

## 检查自动生成的组

接入模型后打开 **模型组**。未被现有组覆盖的新模型通常会自动建立同名故障切换组；名称与现有组近似的模型可能进入待分配列表。

![模型组列表中的成员、分发策略和操作入口](/images/model-groups.png)

保存站点、保存模型组、同步模型和服务启动时都会重新归组。需要了解一次同步的具体变化时，打开右上角的 **同步记录**。

这里的“归组”是把已接入的渠道模型加入模型组；获取上游目录由 [渠道模型同步](./sites#控制自动同步范围) 完成。只修改模型组规则，不会替渠道拉取新模型。

| 归组结果 | 接下来做什么 |
| --- | --- |
| 加入现有组 | 打开该组，确认加入的 Key、上游模型与顺序 |
| 新建同名组 | 检查名称和成员，再决定是否增加别名 |
| 待分配 | 从待分配列表选择归入的执行组，或建立合适的新组 |
| 移除自动成员 | 检查上游模型是否已移除，或组规则是否不再匹配 |

## 设置主备顺序

1. 找到模型组，点击行末 **操作 → 编辑模型组**。
2. 模型组类型选择 **直接调度**。
3. 分发策略选择 **故障切换 (Failover)**。
4. 在 **渠道成员** 中确认 A-Key 和 B-Key 对应的 `gpt-6.1-sol` 均已启用；将 A 放在 B 前面。
5. 保存后执行 **测试模型**，再在请求日志中确认实际使用的上游。

![模型组编辑：策略、匹配条件、渠道优先级和成员](/images/group-editor.png)

| 策略 | 适用场景与行为 |
| --- | --- |
| 故障切换 | 按配置顺序尝试，适合主供应商优先、备用供应商接管 |
| 平滑轮询 | 在可用候选之间分配请求，健康分参与权重 |
| 插件策略 | 已启用的插件提供候选排序；配置方法见 [插件开发](../development/plugins) |

故障切换成功后，默认会在短时间内复用成功成员，减少反复访问刚失败的上游。这个时间由 `failover_affinity_seconds` 控制，默认 30 秒。

因此，“A 排在第一”不代表每次请求都一定调用 A。A 冷却、协议或上下文条件不合适，以及故障后正在复用 B，都可能使 B 先被选中。两把 Key 是两个成员；同一 Key 的多个地址或协议只是调用出口，不会因为多填一个地址就多占一个轮询位置。

## 设置匹配范围

**名称按不区分大小写的“包含”匹配。** 例如组名 `gpt-6` 会同时匹配 `gpt-6.1-sol` 和 `gpt-6-luna`。

填写正则后，名称条件与正则按 **或 / 与** 组合：

- **或**：名称包含条件、正则任意一个匹配就加入。
- **与**：名称包含条件和正则都匹配才加入。

正则默认可以匹配名称的一部分。需要精确名称时，用 `^` 和 `$` 限定开头和结尾，并将模型名中的点写成 `\.`。

| 目标 | 配置示例 |
| --- | --- |
| 接入一类模型 | 组名 `claude`，按名称包含匹配 |
| 只允许精确名称 | 组名 `gpt-6.1-sol`，选择 **与**，正则填 `^gpt-6\.1-sol$` |
| 自定义对外名称并匹配上游 | 组名 `daily-chat`，选择 **或**，正则填 `^gpt-6-luna$` |

本例希望主备模型都严格使用 `gpt-6.1-sol`，所以选择 **与** 并填写 `^gpt-6\.1-sol$`。如果将 `gpt-6` 这样的宽匹配组收窄到一个模型，保存后确认其他型号已不在自动成员中，再调整 A、B 的顺序。

自动匹配会把成员保存到组内。也可以通过 **添加成员** 手动选择，或从待分配列表批量归入。

| 成员来源 | 改变匹配规则后 |
| --- | --- |
| 自动匹配或自动归组 | 重新计算；不再匹配或目标失效时移除 |
| 手动添加或明确归入 | 保留这条成员记录；渠道或模型失效时仍不能用于调用 |
| 已排除 | 后续自动归组跳过，直到恢复该成员 |

如果缩小规则后仍看到某个模型，先检查它是否为手动成员。匹配规则不会替你删除明确手动加入的成员。

移除成员会将它加入该组的已排除列表，后续归组不会立即重新加回；需要时可在组内恢复。合并模型组会把成员和引用转移到目标组，并删除源组及其匹配规则，操作前确认客户端使用的名称。

## 使用别名

如果希望多个对外名称共用一套成员和策略，新建模型组，将类型设为 **别名**，并选择要引用的执行模型组。

本例按以下方式配置：

1. 确认 `gpt-6.1-sol` 是 **直接调度** 类型，包含 A、B 两个成员。
2. 新建 `daily-chat`，类型选择 **别名**，引用 `gpt-6.1-sol`。
3. 用具有 `daily-chat` 权限的网关 Key 发起请求，客户端 `model` 填 `daily-chat`。
4. 在日志中确认请求组为 `daily-chat`，执行组为 `gpt-6.1-sol`。

以后调整执行组成员时，别名会复用这些变化。别名必须直接引用执行组，不支持“别名再引用别名”。如果只是给同一套成员增加一个对外名称，使用别名即可，不必复制成员。

直接调度组也可以用自定义名称加正则建立自己的成员集合，见上面的 `daily-chat` 规则示例；它与“引用已有执行组”的别名是两种配置方式。详细关系见 [系统架构](../development/architecture#别名怎样找到两个候选)。

## 上下文与多模态回退

- **默认上下文**：用于成员未单独设置上下文时的候选过滤。优先填写已知的实际窗口，不靠模型名猜测。
- **上下文不足**：网关按请求估算跳过不足的成员；所有成员都不足时仍交给上游判断，上游确认超限后继续尝试其他成员。
- **多模态备用组**：在高级设置中指定顺序。含多模态内容的请求在主组候选耗尽后，可继续尝试备用组。

对话协议可按成员的上游协议转换；图片、向量和重排入口仍需匹配相应能力。模型组名称本身不会给上游增加能力。

## 验证结果

调用后打开 **请求日志**，检查客户端请求的组名、实际执行组和最终上游渠道。失败请求的详情还会展开各次尝试；成功请求的完整尝试记录可通过管理 API 查询，方法见 [请求排查](./monitoring#定位一次请求)。

如果成员不可用，先检查渠道和模型的启用状态、凭证地址范围以及 [健康状态与冷却](./monitoring#查看健康与冷却)。
